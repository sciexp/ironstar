## ADDED Requirements

### Requirement: committed Cargo.nix kept in lockstep with Cargo.lock

The Rust build substrate SHALL be driven by a `Cargo.nix` committed at the repository root, generated by crate2nix from `Cargo.lock` and `Cargo.toml`.
The committed `Cargo.nix` MUST encode the same set of packages as `Cargo.lock`, and MUST be regenerated whenever `Cargo.lock` or `Cargo.toml` changes.
A regeneration recipe `just regenerate-cargo-nix` MUST be available, and CI MUST auto-regenerate and commit `Cargo.nix` when `Cargo.lock` or `Cargo.toml` change.

#### Scenario: package sets reconcile on a clean tree

- **WHEN** the `cargo-nix-lock-sync` check runs against a tree whose `Cargo.nix` was generated from the current `Cargo.lock`
- **THEN** the `[[package]] name@version` set in `Cargo.lock` equals the `crateName/version` set in `Cargo.nix` and the check passes

#### Scenario: a hand-edited mismatch fails the staleness check

- **WHEN** `Cargo.lock` is bumped without regenerating `Cargo.nix`
- **THEN** the `cargo-nix-lock-sync` check detects the divergence and fails

#### Scenario: CI regenerates Cargo.nix on a lock change

- **WHEN** a pull request changes `Cargo.lock` or `Cargo.toml`
- **THEN** the lock-file regeneration workflow runs `crate2nix generate` and auto-commits the updated `Cargo.nix`

### Requirement: no import-from-derivation in the build substrate

The build substrate SHALL NOT use import-from-derivation.
`Cargo.nix` MUST be committed rather than produced via crate2nix's `generatedCargoNix`, and `nixConfig.allow-import-from-derivation` MUST NOT be added.
`nix build` and `nix flake check` MUST be fully offline, deriving every third-party crate's sha256 from `Cargo.lock` with no `crate-hashes.json` artifact.

#### Scenario: flake evaluates without IFD or network

- **WHEN** `nix flake check` evaluates the flake with no network access
- **THEN** evaluation succeeds and no derivation is built during evaluation to obtain build inputs

#### Scenario: no crate-hashes.json is produced

- **WHEN** `Cargo.nix` is generated for the workspace
- **THEN** no `crate-hashes.json` file is emitted, because all 565 crates.io checksums come from `Cargo.lock`

### Requirement: pinned toolchain threaded into per-crate builds

Every per-crate build SHALL use the pinned Rust toolchain (1.94.1 via rust-overlay).
The toolchain MUST be threaded into `buildRustCrateForPkgs` by overriding `rustc` and `cargo`, so per-crate builds match the toolchain used by formatting and the devshell.

#### Scenario: workspace member builds use the pinned toolchain

- **WHEN** a workspace member is built via `cargoNix.workspaceMembers.<name>.build`
- **THEN** the build uses the pinned 1.94.1 `rustc` and `cargo`, identical to the formatting and devshell toolchain

### Requirement: embedded assets are non-empty

The build SHALL preserve the embedded-asset behavior that crane provides today.
The `ironstar` binary's rust-embed frontend manifest from `../../static/dist` MUST be non-empty, and the `ironstar-analytics-infra` embedded ducklake catalog from `../../assets/ducklake-catalogs` MUST be embedded.
For the two members whose rust-embed reads reach the workspace root, `src` MUST be overridden to re-establish the parent layout above the crate root.

#### Scenario: frontend manifest is non-empty

- **WHEN** the `ironstar` binary is built under crate2nix and its embedded asset manifest is inspected
- **THEN** the manifest from `static/dist` is non-empty, not merely compiling

#### Scenario: ducklake catalog is embedded

- **WHEN** the `ironstar-analytics-infra` crate is built under crate2nix
- **THEN** the embedded catalog tree from `assets/ducklake-catalogs` is present, preserving the empty-embed status quo without breaking the build

### Requirement: migration SQL reads resolve under per-member source

The build SHALL resolve all `include_str!` migration reads correctly under crate2nix's per-member source isolation.
The migration files referenced from `crates/ironstar/src/...` MUST be present in the ironstar member's source tree so the `include_str!` macros compile.

#### Scenario: migration include_str! macros compile

- **WHEN** the `ironstar` crate is compiled under crate2nix
- **THEN** the `include_str!("../../migrations/...")` and `include_str!("../../../migrations/...")` reads resolve to `crates/ironstar/migrations` and compile successfully

### Requirement: per-member test checks and workspace clippy gate preserve test parity

The build SHALL gate test correctness through per-member test checks on the per-crate build graph and SHALL gate lint correctness through a single workspace clippy gate.
Each of the 11 workspace members MUST have a test check derived from `(cargoNix.workspaceMembers.<name>.build.override { runTests = true; testPreRun = "export HOME=/tmp"; }).passthru.test`, reusing that member's existing `buildRustCrate` build rather than compiling from source.
The aggregate check name `workspace-test` MUST be preserved as a zero-build-cost `linkFarm` over the 11 per-member outputs, so the devshell `inputsFrom` and the buildbot/Mergify umbrella names are untouched.
The clippy gate MUST run `cargo clippy --profile dev --locked --all-targets -- --deny warnings` against offline `importCargoLock`-vendored dependencies, with no network and no IFD.
The behavioral envelope MUST be exact parity with the prior cargo-workspace test gate: the per-member sum reconstructs 933 passed / 5 ignored over 938 defined tests, with the 5 network `#[ignore]` tests skipped by default (no `--run-ignored`).

#### Scenario: per-member test checks reconstruct the parity envelope

- **WHEN** the 11 per-member `*-test` checks run and their per-member passed/ignored counts are summed
- **THEN** the sum is 933 passed and 5 ignored over 938 defined tests, exact parity with the prior cargo-workspace test gate, and each per-member check fails by construction on any non-zero test-binary exit

#### Scenario: network ignore tests are skipped by default

- **WHEN** the per-member test checks run without `--run-ignored`
- **THEN** exactly the 5 network `#[ignore]` tests are skipped (2 in `ironstar-analytics-infra`, 3 in the `ironstar` binary member), matching the prior gate's no-`--run-ignored` behavior

#### Scenario: workspace clippy gate denies warnings offline

- **WHEN** the `workspace-clippy` check runs
- **THEN** it executes `cargo clippy --profile dev --locked --all-targets -- --deny warnings` over the `importCargoLock`-vendored dependency set with no network access, and passes with no warnings

#### Scenario: check surface enumerates the named member test checks at count 26

- **WHEN** `nix eval .#checks.<system> --apply builtins.attrNames` is evaluated after the migration
- **THEN** the 11 per-member checks `ironstar-core-test` ... `ironstar-test` and the aggregate `workspace-test` are present, and the total check count is 26 (15 prior + 11 per-member)

#### Scenario: per-crate test and clippy packages are removed

- **WHEN** `nix eval .#packages.<system> --apply builtins.attrNames` is evaluated after the migration
- **THEN** the 20 ad-hoc per-crate `*-test`/`*-clippy` package attributes are absent

### Requirement: build-graph snapshot is a committed, deterministic, non-gating record

The build substrate SHALL commit a build-graph snapshot as a deterministic, non-gating observability record rather than a CI gate.
A committed `modules/apps/build-graph-snapshot/snapshot.json` MUST record the hash-free, sorted, timestamp-free build-graph projection over the canonical Rust-core roots, regenerated on demand via the `build-graph-snapshot` flake app whenever the graph changes.
The snapshot is reviewed on a human cadence, not enforced by a check derivation; workspace-member presence remains hard-gated by the per-member `*-test` checks, so the build graph cannot silently lose a member without a check failing.

#### Scenario: snapshot regeneration is deterministic

- **WHEN** the `build-graph-snapshot` flake app is run twice over an unchanged substrate
- **THEN** it produces byte-identical sorted, hash-free JSON equal to the committed `modules/apps/build-graph-snapshot/snapshot.json`

#### Scenario: no build-graph check gates the surface

- **WHEN** `nix eval .#checks.x86_64-linux --apply builtins.attrNames` is evaluated
- **THEN** `build-graph-invariants` is absent and the total check count is 26

### Requirement: per-dependency-crate cache granularity

The build substrate SHALL produce one `buildRustCrate` derivation per dependency crate so that a single-dependency bump invalidates only that dependency's cone.
A single-crate `Cargo.lock` bump MUST rebuild only the affected dependency crate's derivation cone, not the whole workspace.

#### Scenario: one dependency bump rebuilds one cone

- **WHEN** a single dependency is bumped in `Cargo.lock`, `Cargo.nix` is regenerated, and `nix build --dry-run` is compared before and after
- **THEN** only the affected dependency crate's derivation cone is in the rebuild set, not the entire workspace
